# PlayerDock — совместимость с медиаплеерами

## Принятая стратегия

PlayerDock не должен самостоятельно реализовывать отдельный протокол для каждого проигрывателя, если сообщество уже поддерживает готовый мост.

Порядок подключения:

1. **Нативный MPRIS** — использовать напрямую через общий MPRIS backend PlayerDock.
2. **Готовый MPRIS bridge/plugin** — рекомендовать или документировать стороннее расширение, которое добавляет MPRIS самому плееру.
3. **Официальный API или IPC** — только если готового MPRIS bridge нет либо он не покрывает важные возможности. Для него создаётся отдельный backend, который переводит команды и состояние в общую модель PlayerDock.
4. **Пользовательский адаптер** — резервный вариант для редких программ: явно настроенные локальные команды/скрипты с документированным форматом обмена. Не использовать угадывание по названию процесса, заголовку окна или эмуляцию нажатий клавиш как основной механизм.

Так мы переиспользуем существующую экосистему, а UI и Player Manager остаются независимыми от конкретного приложения.

## Готовые варианты

| Приложение | Способ | Что требуется |
|---|---|---|
| VLC | Встроенный MPRIS/D-Bus backend VLC | Обычно отдельный адаптер PlayerDock не нужен |
| mpv | Плагин [mpv-mpris](https://github.com/hoyon/mpv-mpris) | Установить плагин; он регистрирует стандартный MPRIS-сервис |
| MPD | Мост [mpd-mpris](https://github.com/natsukagami/mpd-mpris) | Запустить мост как пользовательский сервис; он подключается к MPD и публикует MPRIS |
| Quod Libet | Встроенный плагин MPRIS D-Bus Support | Включить плагин в настройках Quod Libet |
| Firefox | Встроенная MPRIS-сессия браузера | Для управления отдельными вкладками есть [MPRIS per tab](https://addons.mozilla.org/en-US/firefox/addon/mpris-per-tab/) и Native Messaging Host [zen-mpris-tabs](https://github.com/Afesant/zen-mpris-tabs) |

### Arch Linux

Для mpv и MPD существуют пакеты в официальном репозитории Arch Linux Extra:

- `mpv-mpris` — [карточка пакета](https://archlinux.org/packages/extra/x86_64/mpv-mpris/).
- `mpd-mpris` — [карточка пакета](https://archlinux.org/packages/extra/x86_64/mpd-mpris/).

Установка выполняется средствами pacman и записывает файлы в системные каталоги. Выполнять её нужно только для соответствующего проигрывателя и с учётом обычных изменений системного раздела при установке пакетов.

Для mpv плагин автоматически публикует MPRIS, после чего PlayerDock обнаруживает его так же, как VLC или другой MPRIS-плеер.

Для MPD мост запускается как пользовательский systemd-сервис. Upstream README предлагает:

```bash
systemctl --user enable --now mpd-mpris
```

Команда предполагает, что MPD уже установлен и доступен на настроенном локальном сокете или порту.

Для Firefox расширение MPRIS per tab требует разрешения на доступ к вкладкам и сайтам, а также установки локального Native Messaging Host. Это необязательная интеграция, а не зависимость PlayerDock.

## Когда нужен собственный backend

Его стоит добавлять только если:

- у приложения нет нативного MPRIS;
- нет поддерживаемого стороннего моста, который можно безопасно рекомендовать;
- приложение предоставляет документированный API, IPC или локальный протокол;
- есть способ определить доступность приложения, получить метаданные и отправить команды без догадок.

Примеры хороших протоколов:

- **mpv JSON IPC** — официальный JSON-протокол через Unix-сокет. Он поддерживает команды, чтение свойств и подписку на события. Документация mpv прямо предупреждает, что IPC не является защищённым сетевым протоколом: в частности, команда `run` способна запускать процессы. Если в будущем PlayerDock добавит прямой mpv backend, использовать нужно только локальный Unix-сокет с ограниченными правами доступа; не открывать TCP-порт и не принимать удалённые подключения.
- **MPD protocol** — отдельный текстовый протокол. Для Rust существует асинхронная библиотека [mpd_client](https://docs.rs/mpd_client/). В PlayerDock предпочтительнее уже готовый `mpd-mpris` bridge; прямой MPD backend нужен только при конкретной необходимости обойти ограничения моста.

У каждого backend должны быть capabilities: например, если конкретный плеер не поддерживает перемотку или громкость через свой API, PlayerDock должен отключить соответствующий элемент управления, а не показывать фиктивную поддержку.

## Инструменты диагностики

[Playerctl](https://github.com/altdesktop/playerctl) — зрелый CLI для MPRIS, а не универсальный контроллер произвольных приложений. Он полезен как независимый инструмент проверки:

```bash
playerctl --list-all
playerctl --player=NAME metadata
playerctl --player=NAME status
```

Если приложение отсутствует в списке, сначала нужно проверить, включён ли его собственный MPRIS-плагин или установлен ли подходящий bridge.

PlayerDock уже использует zbus для MPRIS напрямую. Добавлять зависимость от Playerctl только ради тех же MPRIS-вызовов не требуется.

## Ограничения

Единого протокола, который мог бы управлять любым произвольным приложением, нет. Если программа не публикует метаданные и не предоставляет IPC/API, невозможно надёжно получить название трека, позицию и команды управления универсальным способом.

Поэтому принцип проекта: **сначала готовый MPRIS bridge, затем официальный API/IPC, собственный адаптер — только когда готового решения действительно нет.**
