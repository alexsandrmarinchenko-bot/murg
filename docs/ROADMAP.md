# PlayerDock — архитектура и план развития

## 1. Назначение

PlayerDock — универсальная настольная панель управления медиаплеерами Linux. Приложение не воспроизводит медиа самостоятельно: оно обнаруживает внешние проигрыватели, показывает их состояние и отправляет команды.

Главный принцип: **интерфейс и основная логика не должны зависеть от конкретного плеера**.

Поддержка «всех приложений» не может быть гарантирована одним универсальным способом. Приложение будет поддерживаться автоматически, если оно предоставляет стандартный MPRIS-интерфейс. Для программ без MPRIS потребуются отдельные адаптеры, если у них есть подходящий API или другой стабильный способ управления.

## 2. Состояние исходной версии

На момент начала переработки:

- Rust edition 2024, Slint 1.18.1, zbus 5.
- В `src/player.rs` зафиксировано D-Bus имя `org.mpris.MediaPlayer2.com.badmanners.murglar`.
- В `src/ui.rs` интерфейс напрямую вызывает функции текущего MPRIS-кода.
- Состояние плеера обновляется блокирующими D-Bus запросами по таймеру раз в секунду.
- Обрабатываются Play/Pause, Previous, Next, Seek, Volume, метаданные и локальная обложка `file://`.
- Библиотека и настройки пока заглушки.
- Отдельных автоматических тестов логики плеера нет; CI выполняет `cargo check --locked`.

Текущая интеграция должна остаться рабочей во время постепенного переноса на новую архитектуру.

## 3. Целевая архитектура

### 3.1. Domain / Core

Независимые от D-Bus и Slint типы:

- `PlayerId` — стабильный идентификатор найденного экземпляра плеера.
- `PlayerDescriptor` — имя, приложение, desktop entry и другая доступная информация.
- `PlayerSnapshot` — метаданные трека, статус воспроизведения, позиция, длительность, громкость и обложка.
- `PlayerCapabilities` — перечень поддерживаемых конкретным плеером действий.
- `PlayerCommand` — Play, Pause, PlayPause, Next, Previous, Seek и SetVolume.
- `PlayerEvent` — изменение статуса, метаданных, позиции, доступности или подключения.

UI получает готовые модели и события, а не D-Bus объекты или имена сервисов.

### 3.2. Player Manager

Единый менеджер отвечает за:

- обнаружение доступных проигрывателей;
- хранение списка обнаруженных экземпляров;
- выбор активного плеера;
- запоминание ручного выбора пользователя;
- переключение на другой доступный плеер при отключении выбранного;
- передачу команд нужному backend;
- публикацию обновлённого состояния в UI.

При нескольких одновременно работающих плеерах приложение должно показывать их в списке. Автоматический выбор не должен постоянно перехватывать управление у плеера, которого пользователь выбрал вручную.

### 3.3. Backend / Adapter API

Каждый backend реализует общий контракт: обнаружить или подключить плеер, получить его состояние, сообщать об изменениях и выполнить поддерживаемую команду.

Предполагаемое разделение:

- **MPRIS backend** — общий backend для приложений, публикующих стандартный интерфейс MPRIS.
- **App-specific adapters** — отдельные адаптеры для приложений без MPRIS либо для дополнительных функций, которые стандарт не предоставляет.
- **Player Manager** — работает с общим контрактом и не знает деталей реализации конкретного приложения.

На первом этапе адаптеры будут обычными Rust-модулями, собранными вместе с приложением. Система динамических сторонних плагинов сейчас не нужна.

### 3.4. MPRIS Discovery

Убрать фиксированное имя Murglar и обнаруживать сервисы с префиксом `org.mpris.MediaPlayer2.` в пользовательской D-Bus-сессии.

Обнаружение должно:

1. На старте получить список уже зарегистрированных MPRIS-сервисов.
2. Подписаться на изменение владельцев имён D-Bus.
3. Добавлять новый плеер при появлении сервиса и удалять/помечать отключённым при исчезновении.
4. Создавать отдельный клиент для каждого экземпляра.
5. Запрашивать свойства и проверять реальные возможности, прежде чем показывать или выполнять действие.

MPRIS станет основной интеграцией, а Murglar останется одним из совместимых плееров, а не специальным случаем всего приложения.

### 3.5. Асинхронная работа

Блокирующие вызовы не должны выполняться в потоке интерфейса.

- Вынести D-Bus операции в отдельную асинхронную задачу или worker.
- Использовать сигналы изменения свойств MPRIS, когда они доступны.
- Оставить редкий polling только как резервный механизм.
- Передавать события в Slint через безопасный механизм обновления UI из event loop.
- Отменять задачи и освобождать соединения при отключении плеера.

## 4. Возможности и ограничения

### Базовые функции

- обнаружение и выбор плеера;
- Play/Pause, Next, Previous;
- перемотка и громкость, если их поддерживает плеер;
- название, исполнитель, альбом, длительность и статус;
- обложка;
- отображение недоступных действий без ложных ошибок.

### Возможности конкретных приложений

Не все функции являются частью MPRIS. В частности, стандартный MPRIS не предоставляет универсальный API для просмотра всей музыкальной библиотеки, каталога, плейлистов, авторизации или скачивания.

Поэтому:

- общая панель воспроизведения будет единой;
- дополнительные функции будут появляться только у тех плееров, чей адаптер их действительно поддерживает;
- библиотеку нельзя выдавать за универсально доступную для любого плеера;
- при необходимости можно отдельно реализовать локальный список недавно воспроизведённых треков, с настройкой хранения истории.

### Обложки

Сначала сохранить поддержку локальных `file://` URL. Затем добавить загрузку удалённых `http://` и `https://` обложек с ограничениями размера, тайм-аутом и кэшированием. Ошибка обложки не должна ломать обновление состояния плеера.

## 5. План реализации

### Этап 0. Переименование и уборка

- [x] Переименовать Cargo-пакет и отображаемое имя приложения в PlayerDock.
- [x] Обновить README и команды сборки.
- [x] Сохранить текущую версию отдельной резервной веткой.
- [x] Проверить рабочие изображения и архивы Figma.
- [x] Зафиксировать архитектурный план.
- [ ] Отдельно переименовать slug репозитория GitHub в PlayerDock, когда это будет доступно через настройки GitHub.

### Этап 1. Разделение ядра

- Ввести независимые доменные структуры и типы команд.
- Отделить состояние приложения от Slint.
- Описать общий контракт backend.
- Перенести текущую интеграцию Murglar под этот контракт.
- Добавить mock backend для тестов.

**Готово, когда:** приложение продолжает работать с Murglar, а UI не зависит от его D-Bus имени.

### Этап 2. Универсальное обнаружение MPRIS

- Реализовать поиск всех MPRIS-сервисов.
- Отслеживать подключение и отключение приложений.
- Показывать список плееров и позволить выбрать активный.
- Хранить независимое состояние каждого найденного экземпляра.
- Обработать несколько одновременно работающих плееров.

**Готово, когда:** Murglar, VLC, Spotify и другие приложения с работающей MPRIS-интеграцией обнаруживаются без специальных имён в UI. Фактическая совместимость проверяется на установленных версиях приложений.

### Этап 3. Надёжность и производительность

- Перевести взаимодействие на асинхронную модель.
- Использовать D-Bus signals вместо постоянного полного опроса.
- Проверять capabilities каждого экземпляра.
- Обрабатывать отключения, тайм-ауты и ошибки отдельных команд.
- Добавить unit-тесты и интеграционные тесты D-Bus.

**Готово, когда:** зависший или отключившийся плеер не блокирует интерфейс и не мешает другим плеерам.

### Этап 4. Новый интерфейс

- Сделать единый экран текущего воспроизведения.
- Добавить переключатель обнаруженных плееров.
- Показывать источник воспроизведения и доступные действия.
- Сохранить точные состояния кнопок, hover/pressed и анимации.
- Продумать адаптивную компоновку для разных размеров окна.
- Разделить экран воспроизведения, настройки и дополнительные функции.

**Готово, когда:** смена backend не требует перестраивать основной экран.

### Этап 5. Дополнительные адаптеры

- Проверить приложения, не предоставляющие MPRIS.
- Для каждого выбрать официальный API или другой стабильный интерфейс.
- Добавлять поддержку по одному адаптеру с тестами.
- Выносить специфические функции в capability-модель.
- Не имитировать поддержку функции, если приложение её не предоставляет.

**Готово, когда:** новое приложение подключается отдельным backend без изменений общего UI и ядра.

### Этап 6. Настройки и дополнительные разделы

- Настройки активного плеера и поведения автоматического выбора.
- Настройки обновления состояния, обложек и кэша.
- Локальные избранное/недавние треки — только если пользователь этого хочет.
- Библиотека и плейлисты — через адаптеры, которые реально предоставляют эти данные.
- Хранить настройки в XDG config directory, чувствительные токены — в системном хранилище секретов, если они понадобятся.

### Этап 7. Подготовка выпуска

- Проверки `cargo fmt`, `cargo clippy`, `cargo test`, `cargo check --locked`.
- Linux-сборки и проверка на Wayland/X11.
- Иконка, desktop entry, версия и release artifacts.
- Документация по совместимости и диагностике.
- Проверка поведения при отключении плееров и D-Bus.

## 6. Правила разработки

1. Не переписывать всё приложение одним большим коммитом.
2. Сохранять рабочую интеграцию Murglar до появления полноценной замены.
3. Перед правками исходников создавать резервную копию или отдельную резервную ветку.
4. Не удалять архивы Figma и ресурсы без проверки ссылок и необходимости.
5. Не привязывать UI к названиям конкретных приложений.
6. Каждую новую интеграцию сопровождать тестами и документированием ограничений.
7. После каждого этапа проверять сборку и запуск на Linux.

## 7. Критерий успеха

PlayerDock считается универсальным контроллером, когда умеет автоматически обнаруживать несколько MPRIS-плееров, переключать активный плеер, отображать их состояние и поддерживаемые действия, не блокируя UI. Приложения без MPRIS подключаются отдельными адаптерами, не меняя основное ядро и интерфейс.


## 8. Реализовано в текущем этапе

- Универсальный поиск зарегистрированных MPRIS-сервисов через пользовательскую D-Bus-сессию.
- Получение Identity каждого приложения и переключение между найденными плеерами.
- Команды и чтение метаданных больше не используют фиксированное D-Bus имя Murglar.
- Фоновая проверка опубликованных GitHub Releases при запуске и каждые 6 часов.
- Кнопка обновления отображается только при наличии более новой SemVer-версии и готового Linux x86_64 asset.
- Перед установкой скачанный бинарник сверяется с SHA-256. Помощник заменяет текущий исполняемый файл после закрытия UI и сохраняет предыдущую версию для отката.
- Добавлен GitHub Actions workflow публикации Linux x86_64 release assets по тегам вида `vX.Y.Z`.

**Ограничение обновления:** автоматическая установка рассчитана на пользовательскую, доступную для записи копию исполняемого файла. Системные установки, защищённые правами администратора, не перезаписываются. Опубликованных Releases в репозитории пока нет: первая кнопка обновления появится после публикации первого тега версии с бинарным asset.


## 9. Стратегия интеграций без MPRIS

Принят подход **MPRIS-first / bridge-first**: сначала искать и рекомендовать поддерживаемый сторонний MPRIS-плагин или bridge для самого проигрывателя. Не создавать собственный backend только ради обхода уже существующего решения.

Проверенные примеры и инструкции вынесены в [PLAYER-COMPATIBILITY.md](PLAYER-COMPATIBILITY.md): VLC использует встроенный MPRIS; mpv можно подключить через mpv-mpris; MPD — через mpd-mpris; Quod Libet имеет включаемый MPRIS-плагин; Firefox поддерживает общую MPRIS-сессию, а отдельные вкладки можно экспортировать через внешнее расширение и Native Messaging Host.

Если готового моста нет, следующий выбор — документированный API/IPC самого приложения. Для Rust уже существуют библиотеки, например mpd_client для MPD. Прямой mpv JSON IPC можно рассматривать как специальный backend, но только с локальным Unix-сокетом и строгими правами: протокол не защищён и предоставляет потенциально опасные команды.

Не использовать эмуляцию клавиатуры, scraping заголовка окна и эвристики по имени процесса как стандартный способ управления. Такие методы ненадёжны и не дают единого контракта метаданных, позиции и команд.

Для каждого backend требуется capability-модель: UI показывает только реально поддерживаемые действия. Новый backend добавляется только при наличии конкретного приложения и воспроизводимого сценария тестирования.
